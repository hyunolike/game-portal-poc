# 코드 리뷰 가이드

## 원칙

1. **기계가 잡을 수 있는 건 기계가 잡는다.** 포맷·네이밍·미사용 using 은 `.editorconfig` + `dotnet format` + 빌드 경고=에러로 CI 에서 차단한다. 리뷰에서 스타일 지적은 하지 않는다.
2. **AI 1차 리뷰 → 사람 리뷰.** Claude 가 체크리스트 기반 1차 리뷰를 남기고, 사람은 설계·도메인·트레이드오프에 집중한다. AI 코멘트는 참고 의견이며 승인 권한은 사람에게만 있다.
3. **리뷰는 24시간 내 1차 응답.** PR 은 400줄 이하를 권장한다. 크면 쪼갠다.
4. **코멘트에 등급을 붙인다.**
   - `[필수]` 머지 전 반드시 수정 (버그, 보안, 정합성)
   - `[제안]` 더 나은 방법이 있지만 작성자 판단
   - `[질문]` 의도 확인
   - `[칭찬]` 좋은 코드는 말로 남긴다

## 체크리스트

### 정합성 / 동시성 (재화·보상 관련 코드는 필수)
- [ ] "조회 → 검증 → 수정" 이 애플리케이션에서 일어나 Lost Update 가능성이 있지 않은가? → 조건부 UPDATE / UNIQUE 제약 / 동시성 토큰
- [ ] 외부 API(게임 서버, 결제) 호출이 DB 트랜잭션 안에 있지 않은가? → Outbox
- [ ] 재시도 시 중복 처리되지 않는가? (멱등키)
- [ ] 여러 번의 `SaveChanges` 가 부분 성공할 수 있지 않은가? → 트랜잭션 + `ExecutionStrategy`

### EF Core / DB
- [ ] 조회 전용 쿼리에 `AsNoTracking()` 과 필요한 컬럼만 `Select` 프로젝션
- [ ] 루프 안 쿼리(N+1) 없음
- [ ] 새 WHERE/ORDER BY 조건에 맞는 인덱스가 있는가? 마이그레이션 SQL 을 직접 확인했는가?
- [ ] 대용량 테이블의 인덱스 추가/컬럼 변경 시 락 시간 검토 (`ONLINE = ON` 필요 여부)
- [ ] 페이징 없는 목록 조회 없음 (`PageRequest.MaxPageSize`)

### API
- [ ] 에러는 `DomainError` 코드로 반환 (클라이언트는 메시지가 아닌 코드로 분기)
- [ ] 기존 에러 코드·응답 필드를 바꾸지 않았는가? (웹/런처 하위 호환)
- [ ] 입력 검증은 FluentValidation Validator 로
- [ ] `CancellationToken` 을 끝까지 전달

### 운영툴
- [ ] 새 엔드포인트에 적절한 권한 정책 (`AdminPolicies`) 지정
- [ ] 운영 데이터 변경 엔티티가 `IAuditableEntity` 인가?
- [ ] 대량 작업은 타임아웃·메모리(스트리밍) 고려

### 관측성
- [ ] 로그는 구조화 템플릿 (`"... {CampaignId}"`) 사용, 문자열 보간 금지
- [ ] 개인정보/토큰을 로그에 남기지 않음
- [ ] 장애 추적에 필요한 식별자(AccountId, CampaignId, MessageId)가 로그에 있는가?

### 테스트
- [ ] 버그 수정에는 재현 테스트가 먼저
- [ ] 동시성·DB 제약 관련 로직은 통합 테스트(Testcontainers) 로 검증
- [ ] 테스트 이름은 한글로 "무엇을 보장하는지" 서술

## 머지 규칙

- `main` 보호: PR 필수, CI 통과 필수, 승인 1명 이상 (CODEOWNERS 경로는 해당 오너 승인)
- Squash merge, 커밋 메시지는 [Conventional Commits](../CONTRIBUTING.md#커밋-메시지)
